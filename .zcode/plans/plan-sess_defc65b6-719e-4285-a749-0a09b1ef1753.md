# Shotlin MVP — Implementation Plan

Greenfield build in `/Users/sayan/Documents/IMG GEN` (empty dir). Requirements come from the three Shotlin docs (product architecture, workflow/backend/cost, build instructions). Decisions: **NestJS+Fastify API · Next.js web · separate worker · Docker Compose (Postgres 16+pgvector, Redis 7, MinIO) · mock providers first, OpenRouter/Gemini adapters ready for keys**.

## Repository layout (pnpm workspaces + turbo)

```
docker-compose.yml  (postgres+pgvector, redis, minio + bucket-init)
docs/               (copies of the 3 Shotlin architecture .md files)
CODEBASE_LOG.md     (initialized at repo root, kept updated every stage)
apps/web/           Next.js App Router + Tailwind — customer + admin UI
apps/api/           NestJS (Fastify adapter) — REST API, port 4000
apps/worker/        BullMQ worker — workflow engine, runs generation pipeline
packages/database/  Drizzle ORM schema + drizzle-kit migrations + seed
packages/core/      pure domain logic: Zod schemas, rule engine, cost engine,
                    skill selector, prompt compiler, input validation, states
packages/providers/ adapter interfaces + OpenRouter / Gemini / Mock adapters
packages/platform/  config loader (env), S3-compatible storage (aws-sdk v3 → MinIO),
                    BullMQ queue setup, logger
```

API never calls AI providers for generation; it validates, persists, and enqueues. All AI calls happen in the worker behind logical roles (vision_analyzer, prompt_compiler, image_generator, quality_reviewer, second_reviewer) resolved from `model_registry` config. `MOCK_PROVIDERS=true` env forces deterministic mock adapters so the whole pipeline is testable without keys.

## Stage 1 — packages/database (schema before business logic)
Drizzle migrations for all tables from doc 2 §3:
- Identity: users, user_sessions, (role enum customer/admin).
- Assets: assets (immutable originals; kind: garment/character/candidate/preview/master), characters, environment_presets.
- Workflow: workflows, workflow_versions, workflow_nodes, workflow_node_configs.
- AI config: model_registry (provider enum openrouter/gemini/mock, model_id, logical role, enabled, capabilities JSON), model_price_versions (per-1M in/out tokens; image price by resolution JSON; effective dates), prompts, prompt_versions (Draft/Test/Production/Archived, variables, body), skills, skill_versions, skill_rules (deterministic activation conditions).
- Jobs: jobs (state machine + snapshot of workflow version), job_inputs, job_attempts, job_step_runs, generation_candidates, quality_reviews (strict-schema JSONB + linkage), defects, job_outputs, job_state_events (every transition recorded).
- Cost: cost_events (per provider call: tokens, images, resolution, USD, price version used, FX rate, INR), budget_rules.
- Evaluation (minimal): benchmark_cases, benchmark_runs, feedback.
- pgvector extension enabled (schema supports vectors later; not used in MVP path).
- Indexes on all FKs + job/status/cost query paths. Fresh DB must build entirely from migrations.
- Seed: admin + demo customer; 6 characters; 7 environment presets (Outdoor Natural/Premium, Indoor Premium, Studio Commercial, Festive, Cinematic Fashion, Clean/Minimal); 4 model_registry rows (Qwen3.6-35B-A3B vision, MiMo-V2.5 QA, GLM-4.6V second reviewer, Gemini 3.1 Flash Image generator) with price versions from doc reference values; 7 prompt categories v1 (input quality, garment vision, compiler, image-gen system, quality review, repair, second review); 12 skills v1 + activation rules; default workflow v1 with 10 configured nodes; budget rules (warn ₹15, hard stop ₹20, max 3 attempts, FX 95.78, ₹20/2K planning reserve).

## Stage 2 — packages/core (pure, unit-tested with Vitest)
- Zod strict schemas: GarmentTruthSheet, QualityReview (garment/character/anatomy/realism/environment/technical scores, critical+minor defects, repair instruction, confidence), GenerationSpec, compiled-prompt envelope.
- Job state machine: CREATED→VALIDATING→ANALYZING→COMPILING→GENERATING→REVIEWING→RETRYING→FINALIZING→READY; terminal INPUT_REJECTED/FAILED/BUDGET_STOPPED/MANUAL_REVIEW/CANCELLED.
- Rule engine (deterministic code, not prompts): configurable thresholds (garment≥94, character≥90, realism≥92, anatomy/technical mins, hard-fail defect list, uncertainty band, min reviewer confidence) → PASS/FAIL/UNCERTAIN + reasons.
- Cost engine: token formula, per-resolution image price, FX conversion, node/attempt/job/per-successful-image rollups; price-version-aware.
- Skill selector: evaluates skill_rules against truth sheet + user selections → ordered skill version ids, max-skills cap.
- Prompt compiler (template-first): Layer A system prompt + Layer B skills (priority order, size-capped) + Layer C job facts + Layer D repair instructions (retry attempts only); deterministic ordering + hard char limit.
- Input validation utilities: MIME sniffing, size/dimension limits, sharp decode/corruption check, blur estimate (variance-of-Laplacian threshold).

## Stage 3 — packages/providers + packages/platform
- Adapter interfaces: `analyzeGarment → {truthSheet, usage}`, `generateImage → {candidates[], usage}`, `reviewCandidate → {review, usage}`, plus chat adapter for second review / optional adaptive compile. All adapters return normalized usage; every call site writes a cost_event.
- Mock adapter: deterministic, scriptable (force PASS/FAIL/UNCERTAIN, defect injection) to exercise retries and budget stops.
- OpenRouter adapter (chat completions with image parts, JSON extraction + one schema-repair retry) and Gemini adapter (Google GenAI SDK, image output, resolution/aspect handling) — active when their env keys exist and model provider says so.
- Storage abstraction: putObject/getObject/signedUrl (presigned GET/PUT) over MinIO/S3; asset key conventions.
- BullMQ queue `generation` + client factory; config loader validating env with Zod.

## Stage 4 — apps/api (NestJS + Fastify)
- Bootstrap, env validation, `/health` (DB + Redis + storage), global Zod validation pipe, throttler on generate, CORS with credentials for web origin.
- Auth: register/login/logout/me; opaque session tokens (hashed in user_sessions) in httpOnly cookie; AuthGuard + AdminGuard.
- Uploads: POST /api/uploads (issue presigned PUT + asset id) → POST /api/uploads/:id/complete (HEAD object, run deterministic validation, mark asset usable/rejected). Originals immutable.
- Customer: characters + environments listing; POST /api/jobs (validate selections, snapshot workflow version, enqueue, per-user/per-job limits); GET /api/jobs/:id (status via customer-friendly states), GET /api/jobs/:id/result (preview + signed download links PNG/JPG), GET /api/projects, POST /api/jobs/:id/feedback. No internal prompts/QA internals exposed to customers.
- Admin: models CRUD + role/price assignment; prompts CRUD + new version + publish (immutable production version) + rollback; skills CRUD + versioning + rules + publish; workflow node config GET/PUT (model, prompt version, timeout, thresholds, retry, enabled); quality rules GET/PUT; costs endpoints (today, avg per successful image by 1K/2K/4K, daily, failed, retry, by model/provider, job ceiling/warning) computed from cost_events; jobs list + full inspector payload (inputs, truth sheet, skills, compiled prompt, all candidates, QA per candidate, defects, models, cost per step, final decision); characters/environments CRUD; settings (FX rate, defaults).
- Audit rows for production config changes (admin audit table or log events; keep minimal).

## Stage 5 — apps/worker (workflow engine)
- BullMQ worker with configurable concurrency; loads workflow version snapshot from the job; executes fixed node order: input_check → vision → skill_select → prompt_compile → image_generate → quality_review → rule_engine → (UNCERTAIN → second_review → re-decide) → (FAIL → repair context from defects, reuse truth sheet, budget-checked retry ≤ max attempts) → finalize.
- Each node: read node config (model, prompt version, timeout, thresholds), record job_step_runs (status, refs, error, duration), write cost_events via cost engine.
- Model output → strict Zod parse; one repair/re-ask on invalid JSON, then node failure.
- Budget guard before every retry: estimate next attempt cost vs job ceiling → BUDGET_STOPPED.
- Finalize: master asset preserved, sharp-generated web preview, signed download URLs, final cost rollup, job READY.
- Vitest integration tests with mock providers: happy path (job→READY with cost events), FAIL→repair→retry→PASS, budget stop, input rejection.

## Stage 6 — apps/web — customer
- `/login` (+register), `/generate`: Section A garment upload (main + optional detail refs, input type), B character (cards + upload, gender/age/height/pose), C environment cards, D output (1K/2K/4K, aspect, count 1/2/4), E summary + Generate. No prompt field anywhere.
- `/jobs/[id]` status with polling showing customer-friendly states (Checking references → Preparing garment details → Creating image → Checking quality → Improving result → Finalizing → Ready); failed internals never shown.
- `/jobs/[id]/result`: large preview, download PNG/JPG (signed), generate another, Good/Needs-improvement feedback. `/projects` history (thumbnail, date, garment type, character, resolution, status, download).

## Stage 7 — apps/web — admin
`/admin`: Overview (jobs today, successful images, failed, first-pass acceptance, avg attempts, avg cost/successful image, cost today, resolution mix, top QA failures), Workflow (fixed node chain, per-node config editor), Models, Prompts (list/editor/version/publish/rollback), Skills (list/editor/versions/rules/publish), Quality Rules (thresholds, hard-fail defects, uncertainty band, retries, second-review policy), Budget & Cost (top cards + per-model/provider breakdown + per-job cost trace), Jobs list + full Job Inspector (every step, candidate, QA, defect, cost), Characters, Environments, Settings (FX, defaults, provider keys status — never showing secret values).

## Key guarantees enforced throughout
Model IDs/prices/prompts/skills/thresholds/retry/budget are all admin-editable data (never hard-coded); backend rule engine owns PASS/FAIL; every provider call writes a cost event with price version; jobs store exact workflow/prompt/skill/model versions used; originals immutable; provider secrets backend-only; PostgreSQL system of record, binaries in MinIO; no scope creep beyond MVP (no canvas/video/campaigns).
